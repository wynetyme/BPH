# Paid randomized packs — must-pass specification

Read official policies *as of launch*:
- https://create.roblox.com/docs/production/monetization/paid-random-items
- https://create.roblox.com/docs/production/monetization/developer-products
- https://github.com/Roblox/creator-docs/blob/main/content/en-us/cloud-services/data-stores/player-data-purchasing.md

## Feature requirements
- Keep a meaningful free-to-earn acquisition route; monetization is an optional purchasing path.
- Each paid pack has a unique developer-product ID set in server configuration at deployment (IDs and prices are UNKNOWN until configured). Distinguish pack content from price; if two purchase methods open the same named pack, reward pool must be identical unless prominently disclosed as distinct pack editions.
- Actual numerical outcome percentages must be available *before spending*, including outcome-specific percentages (not rarity only). A visible button labeled **Odds / Details** opens a complete, keyboard/touch navigable list. A bare (i) icon is insufficient per current Roblox documentation.
- For a multi-card purchase, show the independent per-slot possible outcomes, any guaranteed slot, and any aggregate pack-level claim with the correct mathematical interpretation. A per-slot 1% does NOT mean a 1% chance of at least one rare in a 3-slot pack.
- Represent all final outcomes of a roll with exact rational/integer weights when possible, sum to 100% internally, and display rounded values per Roblox policy. Do not expose a group '1% wildcard' without its constituent final outcomes. All eligibility, pity, guarantees, exclusion of owned cards, and paid boosts must update actual player-specific odds *before* purchase.
- `PolicyService:GetPolicyInfoForPlayerAsync` governs `ArePaidRandomItemsRestricted`. Gate UI and server purchase interactions for restricted users; deny paid RNG if policy lookup fails. Provide suitable earnable or guaranteed alternatives. If trading paid outcomes ever exists, check `IsPaidItemTradingAllowed` separately.
- Client may display odds and ask to buy; server controls grant, dice rolls, inventory and ownership.
- Developer products: only `MarketplaceService.ProcessReceipt` grants. Use a durable purchase receipt ledger, atomic/idempotent updates, retries, no double grants across concurrent/replayed receipts, ensure no lost purchases if player leaves, network fails or server shuts down. Grant or durably enqueue the exact pack entitlement when receipt is verified; avoid random reward duplication. Acknowledge with `PurchaseGranted` ONLY after successful durable grant; otherwise `NotProcessedYet`.
- If purchase is processed away from pack opening, award a durable **unopened pack entitlement** on receipt then open on server later, with a single atomic consumption step. Never roll merely because the purchase dialog closes.
- Set up Developer Product price/ID in Creator Hub manually; don't make up a price or ID. If configured prices change, fetch displayed price through supported Marketplace APIs rather than hard-coding.
- State whether products appear outside the experience, and make sure receipts also work when bought outside.

## Tests
1. Each pack's final-outcome probabilities sum to 100% and are generated by the identical function used to roll.
2. Large deterministic simulations approximate declared frequencies within expected sampling variation (don't use stochastic simulation as sole proof).
3. Single & multi-slot, wildcard, guarantee, pity, luck, filtered pools, unlock restrictions and user-specific odds.
4. Restricted player cannot initiate paid random purchase or redeem paid-currency RNG, including through forged remotes; free pack still works.
5. Policy lookup failure safely denies paid RNG but doesn't crash ordinary gameplay.
6. Duplicate receipt handled once; retry after failed DataStore; reconnect/rejoin; two servers; server shutdown; bought while absent.
7. Purchase prompt dismissal grants nothing; receipts not yet committed don't return `PurchaseGranted`.
8. Receipt allocation, pack entitlement, pack opening and inventory persistence survive reconnection with no lost or duplicate items.
9. UI accessible via mouse, touch, controller and keyboard; disclosure available before purchase; actual price accurately displayed.
10. Source-game odds measured and timestamped; don't label demo numbers as shipping release values.

NO live purchase launch until the entire list is evidenced and manually reviewed.
